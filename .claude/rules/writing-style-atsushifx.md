# atsushifx の文章スタイル

技術記事を執筆・レビューするときに参照する、atsushifx 本人の文章上の癖と思考の型をまとめたものです。
「AI が書いた無難な記事」ではなく「atsushifx が書いた記事」に寄せるための実測ベースの指針として使います。

## 0. 前提: 2 つのコーパスと、その役割分担

本ルールは、性格の異なる 2 つの文章群から抽出しています。混ぜて適用すると破綻するため、役割を分けます。

| コーパス                     | 規模                 | 何を取るか                                        | 適用先             |
| ---------------------------- | -------------------- | ------------------------------------------------- | ------------------ |
| Zenn 記事                    | 115 本               | 文体・構成・表記・図表の使い方                    | 記事の書きぶり全般 |
| はてなブックマークのコメント | 8,850 件 (2005-2026) | 思考の型 (何に反応し、どう留保し、何を持ち出すか) | 論の立て方・視点   |

**CONSTRAINT**: ブックマークコメントは私的な短文であり、語尾 (「〜だよね」「〜だなぁ」「〜のでは？」) をそのまま記事へ持ち込まない。
借用するのは**思考の型のみ**であり、口調ではない。

## 1. 記事の骨格

### 1.1 定型セクション (115 本での出現率)

| セクション                  |         出現率 | 扱い                             |
| --------------------------- | -------------: | -------------------------------- |
| `## はじめに`               |            85% | ほぼ必須                         |
| `## 参考資料`               |            68% | 実質必須。URL + 1 行説明の形式   |
| `## おわりに`               |            56% | 推奨。`## まとめ`は 6% と少数派  |
| `## tl;dr`                  |            24% | 長い記事・手順記事で使用         |
| `## 用語集` / `## 技術用語` | 11% (近年 40%) | 未知語の多い記事で使用。近年増加 |

### 1.2 冒頭の型

`## はじめに`の直後は、次のいずれかで入ります。

- 名乗り型 —「atsushifx です。」→ 空行 → 対象の一文定義 (記事全体の 17%、近年 35%)
- 定義先行型 — 名乗りを省き、いきなり「`X`は〜するシステムです。」から入る

どちらでも、**2〜3 文目で対象が何であるかを一文で定義**します。そのうえで「この記事では、〜を解説します」と範囲を宣言します (68% の記事で使用)。

**NOTE**:「この記事では〜」は記事範囲の宣言であり、議題の列挙ではない。1 文で終える限り、`article-writer.prompt`執筆指示 3 の「予告と総括」には当たらない。

### 1.3 結びの型

`## おわりに`は次の順で構成します。

1. この記事で扱ったことの要約 (1〜2 文)
2. 読者が次に到達できる状態、または次回記事の予告
3. 読者への誘い (「〜しましょう」「〜てみてください」)
4. 「それでは、Happy Hacking!」(63%) または「Enjoy!」(16%)

「それでは、」からの締めは 69% の記事で使われる固定句です。`tl;dr`を置いた記事では、`tl;dr`の末尾に「Enjoy!」を置き、記事末を「Happy Hacking!」で閉じる二段構えを取ることがあります。

### 1.4 見出し

- 見出しに**章番号を振る** (56%)。`## 1. 概要`/`### 1.1 詳細`の形式
- 使用レベルは`##` `###` `####`の 3 段まで。`#####`は 115 本すべてで 0 件
- 見出しは扱う対象を指す名詞句にする。作業手順そのままの見出しは避ける

## 2. 文の作り方

### 2.1 一文一行 (最重要)

**1 つの文を 1 行に書き、途中で改行しない**。 段落は空行で区切ります。

実測: 段落あたり平均 1.54 行、1 行だけの段落が 60.6%、3 行以下が 97.3%。

```markdown
`WSL` は、Windows 上で `Linux` を実行するためのシステムです。
仮想マシンやデュアルブートのような複雑な環境構築をせずに、Windows 上で `Linux` を用いた開発を可能にします。

この記事では、`WSL` を有効にして `Debian` 環境を導入する方法を解説します。
```

段落は 1〜3 文で切り、話題が変わったら空行を入れます。5 行を超える段落は 0.9% しかありません。

### 2.2 文の長さ

平均 39.7 文字、中央値 37 文字。81 文字を超える文は 4.3% のみです。

- 40 文字前後を基準にする
- 1 文に条件と結論を詰め込まず、条件を前の文へ切り出す
- 短文だけを連ねない。40 字前後の説明文に、20 字以下の短い断定を挟む

### 2.3 段落の運び

| 位置        | 役割                                             |
| ----------- | ------------------------------------------------ |
| 段落 1 文目 | 話題を提示する。「〜は、〜です」の定義形が多い   |
| 段落 2 文目 | 理由・機構・条件を足す                           |
| 段落末      | 読者にとっての帰結を書く。「〜できます」で締める |

## 3. 語彙と表記

### 3.1 送り仮名・表記の癖

| 項目         | 採用                 | 実測                   |
| ------------ | -------------------- | ---------------------- |
| おこなう     | **行なう**           | 34 本 vs 「行う」2 本  |
| 技術用語     | バッククォートで囲む | 115 本すべてで使用     |
| 英数字・記号 | 半角                 | 全記事                 |
| 表           | 必ず 1 つ以上入れる  | 115 本すべてに表が存在 |

### 3.2 常用する文末

「〜できます」(84%)、「〜になります」(77%)、「〜しています」(59%) が主軸です。
本文はですます調、表・図のセル・箇条書きはである調/体言止めで書きます。

### 3.3 使わない語

実測で 0 本だったもの。意識せずとも避けられている表現です。

- 一人称「私は」「僕は」「俺は」「わたしは」— いずれも 0 本
- 「〜かもしれない」— 0 本
- 「不可欠」— 2 本のみ

### 3.4 結びに限って許容する表現

`article-writer.prompt`執筆指示 1 A 帯は「〜しましょう」を制限しています。
執筆指示 3 は「〜でしょう」を制限しています。
いずれも実測では、「〜しましょう」が 44 本 (38%)、「〜でしょう」が 24 本 (21%) の記事で使われています。

「〜しましょう」44 本の出現位置を調べた内訳は次のとおりです。

| 出現位置                        | 本数 | 内容                                                             |
| ------------------------------- | ---: | ---------------------------------------------------------------- |
| `## おわりに` / `## まとめ`のみ |   27 | 記事末の読者への誘い                                             |
| 本文にも出現                    |   17 | 大半は`edu-*`学習シリーズの**節末まとめ**、および`elpha-*`の対話 |

```text
このシリーズを通じて、自分の開発スタイルに合った `Linux` 環境を身につけましょう。   ← 記事末
これらの演算はプログラムの制御で大事になる演算です。ぜひ、理解しておきましょう。    ← edu-* の節末
実際の開発に必要な設定を加えて、自分だけの快適な環境を構築できるようになるでしょう。 ← 記事末
```

手順の途中や機能説明では使われていません。

**CONSTRAINT**:「〜しましょう」「〜でしょう」は`## おわりに` `## まとめ` `## tl;dr`の結び、
および学習教材形式の記事における節末のまとめにのみ使用する。手順・機能説明の本文では従来どおり使わない。

## 4. 図表の使い方

| 要素           | 使用率         | 使いどころ                               |
| -------------- | -------------- | ---------------------------------------- |
| 表             | 100%           | 比較・一覧・オプション。最低 1 つは置く  |
| 番号つきリスト | 65%            | 手順                                     |
| mermaid        | 11% (近年 45%) | フローチャート。`sequenceDiagram`は 0 件 |
| `:::message`   | 11%            | 注意喚起・前提の但し書き                 |
| 引用`>`        | 21%            | 一次資料の原文引用                       |
| gist 埋め込み  | 16%            | 自作プロンプト・設定ファイルの全文公開   |

### 4.1 図表キャプション

図・表には番号つきキャプションを斜体で付けます。

```markdown
*図1-1: ClaudeがTDDを誤解し、テストを後付け・改変する誤動作の流れ*
*表2-1: Claudeメモリーファイルの適用範囲*
```

### 4.2 ✅ / ❌ の対比

良い例と悪い例をコードブロックと表の両方で並べる書き方をします。判断基準を読者へ渡すための型です。

### 4.3 参考資料の形式

```markdown
### Webサイト

- [リンクテキスト](URL)
  そのページが何を説明しているかの 1 行
```

URL の直後に必ず 1 行の説明を付けます。リンクの羅列にしません。

## 5. 思考の型 — AI 臭さを消す本体

ここが、体裁だけ整った記事と atsushifx の記事を分ける部分です。
以下はブックマークコメント 8,850 件から抽出した、反応の型です。**記事本文では、ですます調に翻訳して使います。**

### 5.1 歴史的前例に接続する

新しい技術を、過去の同型事例へつなぎます。最頻出の型です。

> 「アイデア勝負 → ゲームの完成度 (=資金勝負) → IP 頼みという流れで、昔からのゲームの発展と一緒だと思う」
> 「eXtreme Programming での Sit together、SCRUM でのプロダクトオーナーなど、ビジネス視点での知見を開発に入れろというのは、昔から散々言われている」

記事へ持ち込むときの形:

```text
この考え方自体は新しくありません。
eXtreme Programming の Sit together や、SCRUM のプロダクトオーナーが同じ問題を扱っています。
```

### 5.2 区別すべきものを切り分ける

一括りにされた語を、定義で割ります。

> 「ハードウェアを仮想化してコードの対象にするのが IaC、サーバ構築・環境設定をコードによって自動化するのが CaC ってところ」
> 「それこそ、本来の DRY (コードではなく、意味のある情報は繰り返さない) ですむ話では」

用語を導入したら、**似た語との境界を一文で示す**。これは`article-review.prompt`レビュー指示 2「同一視の回避」と同じ軸です。

### 5.3 運用・実務の懸念を足す

技術の説明で終わらせず、動かし続ける側の問題を 1 つ挙げます。

> 「で、軍事力を強化したとして。メンテする人や、材料はどうするの」
> 「ソースを読んでみたが、OSS ライセンスが見つからなかった」
> 「ローカルで mcp サーバを使うなら、オンデマンドでサーバ立ち上げですむようになるのかな。そうなればリソースを食わなくなって嬉しいけど」

記事では、節の終盤に「ただし、〜」「一方で、〜」として置きます。

### 5.4 同意の範囲を限定する

全面肯定・全面否定をせず、賛成する部分と留保する部分を分けます。

> 「ビザンチン将軍問題の解決に触れていないのはおかしいが、BitCoin のデキが悪いというのは同意」
> 「デザインパターンは本質としては合っているけど、パターンランゲージとかの広い意味で使っているので注意」

**構文**:「〜は〜だが、〜は〜」。逆接で終わらせず、逆接のあとに論を進めます。

### 5.5 一次情報・別ソースを差し込む

コメントの 7.9% に URL が入ります。主張の裏づけを外部へ置く癖です。
記事では`## 参考資料`に加え、**本文中でも該当箇所に直接リンクを張る**。

### 5.6 条件つきで述べる

断定より、条件と見込みで書きます。ブックマークでの語尾分布は「けど」9.9%、「そう」8.7%、「かな」7.3%、「だろう」5.6%、「かも」4.3%。

**CONSTRAINT**: 記事本文では、この留保を語尾ではなく**条件節**で表現する。
「〜かもしれません」ではなく「〜の場合は、〜になります」「〜であれば、〜が期待できます」の形にする。
`article-writer.prompt`執筆指示 3「弱い緩和」の禁止と、この癖を両立させるための唯一の書き方です。

### 5.7 言い差し・体言止めで止める

ブックマークコメントの 81.9% が句点なしで終わります。すべてを言い切らない癖です。
記事では、**表のセル・図のラベル・箇条書き**でこれを使います。本文では使いません。

### 5.8 自分の環境で動くかを判定軸にする (最頻)

近年のブックマーク 75 件を反応型で分類したところ、最も多いのが「自分の環境で使えるか」への引き寄せでした (約 17〜18 件)。
とくに**Windows ネイティブでの制約**が繰り返し判定軸になります。

> 「Windows だと mise 移行に不安」
> 「Scoop + BusyBox で問題なく使っている」
> 「日本の場合、Android スマートフォンでも Qi に対応していないから困る」

記事へ持ち込むときの形:

- 前提環境の節を、導入手順より**前**に必ず置く
- Windows が対象実行環境に含まれる場合は、固有の注意 (`Git Bash`、パス区切り、権限、改行コード) を明示する
- 「動く/動かない」の境界条件を書く。読者が自分の環境へ写像できる形にする

**NOTE**: 記事群が WSL・PowerShell・Scoop・Windows 環境に集中している理由がここにある。読者の環境判定を助ける点に、この著者の記事の実用価値がある。

### 5.9 一次ソースを自分で確認してから書く

主張の裏づけを、公式ドキュメントの一段下まで確認する癖があります。

> 「README にも書かれているが、`.gitmodules`をみると find, grep は uutils そのままみたい」
> 「ソースを読んでみたが、OSS ライセンスが見つからなかった」

記事では、仕様を書くときに**確認した場所を示す**。確認できなかった項目は、推測で埋めず「公式ドキュメントに記載なし」と書きます。

### 5.10 手放しで褒めない

近年のブックマーク 75 件のうち、全面肯定は 3〜4 件のみでした。残りは必ず何かを足すか正しています。
補足・訂正・拡張 (§5.1/§5.2/§5.4) を合わせると全体の約 3 分の 1 を占めます。

**CONSTRAINT**: 他者のツール・手法を紹介するときは、利点の列挙で終えない。
適用範囲の限定、実務上の懸念、先行する同型事例のいずれかを 1 つ以上添える。

## 6. 記事の種別

すべての記事に同じ型を当てません。実測で 3 系統あります。

| 種別             | 例                                          | 特徴                                            |
| ---------------- | ------------------------------------------- | ----------------------------------------------- |
| 手順・導入記事   | `wsl2-*`, `dev-proxmox-*`, `winhack-*`      | 章番号、番号つき手順、スクリーンショット、表    |
| 設計・方法論     | `claudecode-settings-bdd-style`, `ci-gha-*` | 課題提示 → 既存手法の限界 → 自作手法 → 設計意図 |
| キャラクター対話 | `elpha-*` (エルファ / 小紅 / つむぎ)        | 会話形式。指示がない限り採用しない              |

**CONSTRAINT**: キャラクター対話形式は`elpha-*`シリーズ固有。明示的な指示がある場合のみ使う。

### 6.1 設計・方法論記事の展開

自作の手法を紹介するときの順序が固定されています。

1. 日常の作業で起きた具体的な不都合を書く
2. 既存手法 (他人の手法) を名指しで挙げ、敬意を払ったうえで限界を示す
3. 自分の手法に名前を付ける (`atsushifx式BDD`など)
4. 差分を箇条書きで示す
5. 設計意図を「なぜこの制約を置いたか」として説明する
6. MIT ライセンスで全文を公開する

**NOTE**: 手法に自分の名前を冠する、プロンプトや設定を gist で全文公開する、という 2 点は一貫した振る舞い。

## 7. 読んでいるもの (影響源)

ブックマーク 21,317 件・2005〜2026 年の 21 年分から。

### 7.1 媒体の変遷

| 期間      | 傾向                                                                    |
| --------- | ----------------------------------------------------------------------- |
| 2005-2015 | `moongift` (OSS 紹介)、`sourceforge.jp`、`slideshare`、`d.hatena.ne.jp` |
| 2016-2026 | `zenn.dev`、`qiita.com`、`publickey1.jp`、`github.com`、`note.com`      |
| 通期      | `ryuzee.com` (アジャイル)、`infoq.com`、`cpplover.blogspot.com` (C++)   |

OSS ツールの新着を長期に追い続ける習慣、アジャイル/開発プロセス論への継続的な関心、
ニュースサイトからの技術動向の追跡が、§5.1「歴史的前例に接続する」癖の下地になっています。

### 7.2 好んで読む記事の形 (近年の技術記事 16 本を実読)

| 観点   | 傾向                                                                          |
| ------ | ----------------------------------------------------------------------------- |
| 主題   | 実践と設計論の中間帯。純粋な入門記事・純粋な論文解説はほとんど読まない        |
| 領域   | 開発環境・ツールチェーン > AI コーディングの運用論 > セキュリティ > 業界批評  |
| 文体   | です・ます / だ・である は半々。文体そのものは選好に影響しない                |
| 出所   | 一人称が入り、経験由来だと分かる記事 (16 本中 11 本)                          |
| 見出し | 体言止め主体。`問題1:` `Step 1:` `攻撃シナリオ1:`の番号つきラベル型           |
| 長さ   | 2,500〜4,000 字が主流。手を動かす系なら 8,000 字超、小ネタなら 1,200 字も読む |
| 図表   | 表より**コードブロック優位**。図が多い記事にはむしろ図の使い方へ注文が付く    |
| 題名   | 主張が題名に出ている記事を選ぶ。中立的なまとめ記事はほぼ読まない              |

**NOTE**:「骨格が見える記事を選び、骨格が見える記事を書く」が一貫している。
`## tl;dr` → `## はじめに` → `## 用語集` → `## 1.` `## 2.` → `## おわりに`という固定骨格は、読んでいるものの反映。

### 7.3 読むものと書くものの接続

- mizchi「Cline に自分をエミュレートさせて技術記事を代筆させてみた」へ寄せたコメントは「writer/review/proofreading のプロンプトを使って書いている」。
  これがそのまま本リポジトリの`tech-articles-prompt/` 3 ファイル構成になっている
- 「読解力」記事への「図解しろ。意味のある塊とそれらの関係性で図解できるはず」という反応と、
  DSL 側の「本 DSL は実行系ではなく、LLM との構造認識共有が目的」は同じ発想。文章を「塊と関係」に還元する読み方が、形式言語での指示に転写されている
- 「まず定義を正す」「まず一次ソースを見る」姿勢が、レビュー用プロンプトの肥大と対応する。書く前段のチェック工程に重みを置く

**NOTE**: この節の分析は近年の技術系ブックマーク 75 件のうち、本文を取得できた 16 件に基づく。
ニュース系 (itmedia/zdnet/ascii/gihyo/speakerdeck) 約 23 件はタイトルとコメントのみからの判断。

## 8. 既存プロンプトとの優先順位

本ルールは`tech-articles-prompt/article-writer.prompt`を置き換えません。補完します。

| 順位 | 規則                                                                |
| ---- | ------------------------------------------------------------------- |
| 1    | `:remark` (ユーザーの個別指示)                                      |
| 2    | 執筆指示1 の S 帯 (固有表現保持・技術的正確性・非レビュー領域)      |
| 3    | 本ルール §3.4 (結び限定の解禁) — 執筆指示1 A 帯・執筆指示3 を上書き |
| 4    | 執筆指示3 の禁止語彙・執筆指示4 の CONSTRAINT                       |
